# The core in Rust, C++ or C: plans for later

Written 2026-10-24, beside [core.md](core.md), which chose Go. Here is what
changes if the core, or all of git-board, is ever written in another
language. The milestones (M1–M6), the scope of version 1 and the clean-room
rules stay the same. The scores behind the choice are in the "The fork,
drawn" artifact: Go 8.0, Rust 7.1, C++ 3.5, C 3.5.

## What every implementation shares

- **The spec is the contract.** The refs (`refs/board/<kind>/<id>`), the pack
  JSON, the clock and the order rule, and the operation kinds are the same in
  every language. A repository written by one implementation reads the same
  in any other.
- **A shared test corpus.** M2 adds `spec/testdata/`: small repositories (as
  git bundles) with the state each must load to, as JSON. Every
  implementation runs them. That corpus is what makes a port checkable.
- **git through the `git` binary** for `update-ref`, fetch and push, in every
  language. Only reading and writing objects needs a library.
- **git-board's HTTP API stays the same,** so the web app (19,000 lines of
  Vue and TypeScript) moves over unchanged. A rewrite of git-board ports the
  server and the TUI, not the web app.
- **Port by use.** git-board's 22,000 lines of Go tests are the checklist of
  behaviours to keep or drop, one at a time.
- **MIT:** every library below is checked for it.

## Rust

**When it would win:**
- the core must be used outside git-board, from Python (PyO3) or in the
  browser (WebAssembly);
- or the compiler's guarantees (no data races, exhaustive matches over the
  operation kinds) matter more than compile time.

**Layout:** a cargo workspace.

| Crate | Holds |
|---|---|
| `board-core` | git store, operation log, issues, people, the index |
| `board-sync` | the engine |
| `board-forge` | the forge trait, the fake forge, the conformance suite |
| `board-github`, `board-gitlab` | the adapters |
| `git-board` | the binary: server, TUI, command line |

**Libraries:**

| Need | Crate | Licence |
|---|---|---|
| git objects | `gix` (gitoxide) | MIT / Apache-2.0 |
| JSON | `serde`, `serde_json` | MIT / Apache-2.0 |
| index and search | `rusqlite`, feature `bundled` (SQLite compiled in) | MIT; SQLite is public domain |
| HTTP client | `reqwest` with `rustls` (no OpenSSL) | MIT / Apache-2.0 |
| GitHub's GraphQL | `cynic` | MPL-2.0: fine to link, changes to cynic itself stay MPL |
| server | `axum`, `tokio` | MIT |
| TUI | `ratatui`, `crossterm` | MIT |
| command line | `clap` | MIT / Apache-2.0 |
| web app in the binary | `rust-embed` | MIT |
| tokens | `keyring` | MIT / Apache-2.0 |

**Builds and releases:** cargo, and `cargo-zigbuild` for linux and darwin
(x86_64, aarch64) and windows from one machine. Zig's C compiler also
builds the bundled SQLite.

**Compile time, the main cost:**
- small crates, so that an edit rebuilds one;
- `cargo check` in the edit loop;
- a fast linker (mold on Linux), and sccache in CI;
- few procedural macros in `board-core`.

Expect a clean build in minutes, and seconds to tens of seconds after an
edit. Measure it in M1, before deciding anything else.

**Agent hours:** 160–320 for everything (the core, the sync, both adapters,
git-board's server and TUI, the switch).

**Risks:**
- async code (tokio) spreads through the engine;
- fewer people can review it;
- gitoxide's push is young (fine, since push goes through `git`).

## C++

**When it would win:** hard to see for this project. It brings C's memory
risks and none of Rust's guarantees. Pick it only if a team that already
lives in C++ takes the core over.

**Layout:** CMake, with libraries pinned in a vcpkg manifest. Targets:
`board_core` (static library), `board_sync`, `board_github`,
`board_gitlab`, and the `git-board` executable.

**Libraries:**

| Need | Library | Licence |
|---|---|---|
| git objects | libgit2 | GPL-2.0 with a linking exception: an MIT program may link it |
| HTTP client, TLS | libcurl, with the platform's TLS (OpenSSL on Linux) | curl (MIT-like); OpenSSL is Apache-2.0 |
| JSON | nlohmann/json | MIT |
| index and search | SQLite (FTS5) | public domain |
| server | cpp-httplib | MIT |
| TUI | FTXUI | MIT |
| command line | CLI11 | BSD-3 |
| web app in the binary | generated byte arrays (CMake) | |
| tokens | each platform's own API, by hand | |

**Builds and releases:** CMake presets per platform, statically linked, a
toolchain for each.

**Compile time:** templates and headers make it slow. Mitigate with
precompiled headers, unity builds and ccache.

**Safety:** AddressSanitizer and UndefinedBehaviorSanitizer in CI, and
fuzzing of the pack parser and of the forges' JSON.

**Agent hours:** 220–450.

**Risks:**
- memory bugs in the code that writes issues;
- the build matrix;
- reviewers.

## C

**When it would win:** never, for git-board itself. The case is a tiny,
read-only core embedded in other languages through the C ABI, where Rust
isn't allowed.

**Layout:** meson. A static `libboard` (core and sync), the adapters, and
the `git-board` executable.

**Libraries:**

| Need | Library | Licence |
|---|---|---|
| git objects | libgit2 | GPL-2.0 with a linking exception |
| HTTP client, TLS | libcurl | curl (MIT-like) |
| JSON | jansson | MIT |
| index and search | SQLite (FTS5) | public domain |
| server | civetweb | MIT. Not mongoose, which is GPL or commercial |
| TUI | notcurses | Apache-2.0 |
| web app in the binary | `xxd -i`, or `#embed` with a C23 compiler | |
| GitHub's GraphQL | query strings by hand, and jansson | |

**Memory:**
- one arena per request and per sync run, freed at once;
- AddressSanitizer, UndefinedBehaviorSanitizer and valgrind in CI;
- fuzzing (libFuzzer) of the pack parser and of every forge response.

**Builds and releases:** meson cross files per platform. Windows through
MSYS2 or MSVC.

**Compile time:** fast, close to Go's. That's C's one advantage here.

**Agent hours:** 250–500.

**Risks:**
- memory bugs in the code that writes issues;
- everything by hand (HTTP, JSON, maps, strings);
- the fewest reviewers able to judge it safe.

## If one is ever started

1. Rebuild the M1 trial in that language against the same spec and the same
   test corpus, and measure compile time and size.
2. Compare those numbers with the Go trial's, in the spec's decisions page.
3. Then decide, as for Go: go on, or stop.
